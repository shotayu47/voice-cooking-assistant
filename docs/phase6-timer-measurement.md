# PHASE 6 事前計測 — iPhone 実機テスト手順

**目的**: 複数タイマーの設計（永続化するか／通知を出せるか／背面で何が止まるか）を
推測ではなく実測で決める。**この計測結果が出るまで PHASE 6 の本実装には入らない。**

計測ページ: `https://voice-cooking-assistant-focb.vercel.app/diagnostics/timer`

ログイン済みでないと開けません（既存の認証ゲートのまま）。
どこからもリンクしていないので、URL を直接開いてください。

---

## 共通の準備

- 各テストの最初に **「診断データを消去」** を1回押す（前回の記録が混ざらないように）
- Test A の前だけ **設定 → 画面表示と明るさ → 自動ロック → なし** にしておく
  （A は画面がついたままである必要があるため。C の前に元に戻す）
- 画面を見る場所は3つ: 上の **タイマー** / 真ん中の **interval・ページの状態** / 下の **イベントログ**

---

## Test A — フォアグラウンド（基準値）

画面をつけたままなら interval が素直に動くか。他のテストの比較基準になります。

1. Safari で `/diagnostics/timer` を開く
2. 「診断データを消去」を押す
3. **「5分タイマー開始」** を押す
4. **画面をつけたまま5分待つ**（アプリを切り替えない・ロックしない）
5. 5分経ったら記録する

記録する値: `発火回数` / `直近の発火間隔` / `最大ギャップ` / `実経過` / `tick由来の経過` / `残り`

> 期待: 最大ギャップが 1000ms 前後、`tick由来の経過` ≒ `実経過`。
> ここが既にズレるなら、フォアグラウンドですら interval は信用できないということ。

---

## Test B — バックグラウンド（ホーム画面へ）

1. 「リセット」→ **「10分タイマー開始」**
2. **30秒**待つ
3. 下から上にスワイプして**ホーム画面へ**（Safari を背面に）
4. **3分**待つ（画面はつけたままでよい）
5. Safari に戻る
6. 記録する

記録する値:
- `残り` / `実経過` / `tick由来の経過` / `最大ギャップ` / `復帰回数`
- イベントログの **`visibilitychange → visible`** の行を**そのまま書き写す**
  （実経過・perf経過・ずれ・背面中の tick 回数 が入っています）
- `pagehide` / `pageshow` の行が出たか。出たなら `persisted=` の値

> 見たいこと: 背面の3分で tick が何回発火したか（想定180回に対して何回か）。
> そして **`残り` が正しいか** — deadline 基準なので、ページが生きていれば正しいはず。

---

## Test C — 画面ロック

1. 自動ロックの設定を元に戻してよい
2. 「リセット」→ **「10分タイマー開始」**
3. **30秒**待つ
4. **電源ボタンで画面をロック**
5. **3分**待つ
6. ロックを解除して Safari に戻る
7. Test B と同じ値を記録する

> 特に見たいこと: **`ずれ`（実経過 − perf経過）**。
> ここが大きいなら `performance.now()` はロック中に止まっている＝
> 経過時間の計算に使ってはいけない、という結論になります。

---

## Test D — 長時間バックグラウンド（プロセス破棄の検出）

いちばん重要。**タイマーを永続化する必要があるかどうかがここで決まります。**

1. 「リセット」→ **「10分タイマー開始」**
2. **`instance ID` と `起動回数` をメモする**
3. ホーム画面へ戻り、**他のアプリを2〜3個使う**（カメラや地図など重いものが望ましい）
4. **15分以上**放置する（できれば30分）
5. Safari に戻る
6. 記録する

記録する値:
- `この起動の種類`（3種類のうちどれか）
- `instance ID` が 2. でメモしたものから**変わったか**
- `起動回数` / `前インスタンスの最終イベント`
- `残り` が正しいか（本来の残り時間と合っているか）
- イベントログのいちばん上の **`起動 (...)`** の行をそのまま書き写す

判定の読み方:

| 表示 | 意味 |
|---|---|
| `instance ID` が変わらない | ページは生き残った。永続化は不要かもしれない |
| `再読み込み — タブのセッションは生存` | ドキュメントは作り直された。**メモリ上のタイマーは消えている** |
| `新しいセッション — sessionStorage が失われた` | セッションごと破棄。**永続化必須** |

## Test E — 通知と Service Worker

1. 「この端末で使えるもの」パネルを**そのまま書き写す**
   （standalone起動 / display-mode / navigator.standalone / Notification API /
   Notification.permission / Service Worker API / 登録済み Service Worker /
   freeze・resume / secure context）
2. **「通知権限をテスト」** を押す
3. 許可ダイアログが**出たか出なかったか**を記録
4. 出たら「許可」を選び、`Notification.permission` がどう変わったか記録
5. イベントログの `通知テスト` の行を書き写す

> ページを開いただけでは権限を要求しません。押したときだけです。

## Test F — standalone（任意・最後に）

ホーム画面に追加した PWA として起動したときの挙動。**Test A〜E が終わってから**やってください。

⚠️ 注意: **既存の TSUGU アイコンは消さないでください。** これは別の追加アイコンです。
テストが終わったら新しい方だけ削除して構いません。

1. Safari で `/diagnostics/timer` を開く
2. 共有 → **ホーム画面に追加** → 名前を「TSUGU診断」などにして追加
3. **新しく追加したアイコン**から起動する
4. **開いた画面がどちらか**を記録する
   - **診断ページが開いた** → 成功。`display-mode` と `standalone起動` を記録し、
     **Test B・C・D を同じ手順でもう一度**やる（これが本命のデータ）
   - **TSUGU の通常ホーム画面が開いた** → iOS が manifest の `start_url` を優先した、
     ということ。**その事実だけ記録して終了**してください（それも立派な計測結果です）

> `start_url` は変更していません。変えるとインストール済み PWA が別アプリ扱いになり、
> ログイン状態が壊れるためです。

## この結果から決めること

| 計測結果 | PHASE 6 の設計への影響 |
|---|---|
| Test D でプロセスが破棄される | タイマーを DB か storage に永続化する必要がある。破棄されないなら不要 |
| Test C で `perf経過` が止まる | 経過時間に `performance.now()` を使わない。`Date.now()` と deadline のみ |
| 背面で tick がほぼ止まる | 表示更新は復帰時に deadline から再計算する。カウントで進めない |
| Notification が使えない | 「鳴らす」手段が無い。復帰時に「タイマーは終わっています」と見せる設計になる |
| Notification が使える | Service Worker と Web Push の導入可否を別途検討する（今回は導入していない） |
| standalone で挙動が変わる | 実際の利用形態は PWA なので、そちらの数値を優先する |

計測が終わったら `docs/implementation-roadmap.md` の PHASE 6 の 🔒 を外し、
結果をこのファイルに追記してから本実装に入ること。

**計測環境**: iPhone / Safari タブ

**開始直後の状態**

開始直後（17:19:36）のスクリーンショットでも instance ID は `22dc9697`、
起動回数は0回、この起動の種類は「初回（この端末で初めて開いた）」だった。

**`visibilitychange → visible` の行**

```text
17:51:34 visibilitychange → visible
実経過 31:41 (1901065ms) / perf経過 31:41 (1901075ms) / ずれ -10ms / 背面中の tick 2回 (想定1901回)
```

**関連イベントログ**

```text
17:51:34 focus
17:51:34 focus
17:51:34 interval gap
31:41 (1900575ms) (想定1000ms) / perf 31:41 (1900585ms) / ずれ -10ms / visibility hidden
17:19:53 visibilitychange → hidden
17:19:53 blur
17:19:34 timer start
10分 / deadline 17:29:34 (1786177774849)
17:18:45 reset
```

**ログ先頭の「起動 (...)」の行**: 確認できず。計測前に「診断データを消去」を実行しているため、
今回のスクリーンショットに表示されているイベントログには起動行が残っていない。

**判定**: 31分41秒の長時間バックグラウンド後も instance ID は `22dc9697` のままで、
起動回数も0回、前インスタンスの最終イベントも `—` のままだった。したがって、
**今回の条件では Safari のページプロセス破棄・再起動は発生しなかった**と判断できる。
一方、背面中の tick は想定1901回に対して2回だけで、interval は長時間ほぼ停止した。
それでも `Date.now()` と `performance.now()` は31分41秒ほぼ同じだけ進み、ずれは -10ms に
とどまった。10分の deadline を大幅に過ぎた復帰時も残りは0:00と正しく、deadline 基準の
残り時間計算は長時間バックグラウンドでも機能した。

ただし、この1回で「iOS Safari が長時間でもプロセス破棄されない」と一般化はできない。
メモリ圧迫やOS判断によって破棄される可能性は残るため、複数タイマーの設計では
**interval の継続を前提にせず deadline を正として復元できる設計**が必要であり、
プロセス破棄時の永続化要否は追加条件も含めて判断する。

Notification APIがないため、これらだけでは通知を実現できない。Safariタブでの結果と
standalone PWAでの結果は分け、PWA側の可否はTest Fで確認する。

### Test F — standalone（ホーム画面PWA）

**計測日**: 2026-08-08  
**操作**: Safariの診断ページを「TSUGU診断」という名前でホーム画面へ追加し、
新しく追加したアイコンから18:04に起動。

| 項目 | 実測結果 |
|---|---|
| 新しいアイコン名 | TSUGU診断 |
| 新しいアイコンから開いた画面 | ログインページ |
| 診断ページが開いたか | 開かなかった |
| TSUGUの通常ホームが開いたか | 開かなかった |
| standalone側でログイン状態が認識されたか | 認識されなかった |
| display-mode | 診断ページへ到達できず計測不能 |
| Test B相当 | 未実施 |
| Test C相当 | 未実施 |
| Test D相当 | 未実施 |

**判定**: ホーム画面に追加した「TSUGU診断」アイコンから起動すると、診断ページでも
TSUGUの通常ホームでもなくログインページが表示された。Safariタブで利用していた
ログイン状態が、新しく追加したホーム画面PWAでは認識されず、認証ゲートによって
ログインページへ移動したと考えられる。

認証ゲートが本来の起動先を表示する前にリダイレクトしたため、iOSが追加時の
`/diagnostics/timer` を開こうとしたのか、manifestの `start_url` を優先したのかは、
この画面だけでは判定できない。同様に、診断ページ内の `display-mode`、通知機能、
Test B・C・D相当のstandalone実測値も取得できなかった。したがって、Safariタブの
TEST A〜Eは有効だが、standalone PWAでのタイマー・通知挙動は現時点では未確認。
