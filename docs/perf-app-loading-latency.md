# アプリ全体のスケルトン表示が長い問題 — 調査と第1手

**Status: リージョン変更を適用し、Production で効果を実測。**
`/login` の median −29%、5 秒超の発生率 25% → 0%（§4-B）。
**認証済み画面の改善幅は未計測。**

「どの画面へ移動してもスケルトンが長く出続ける」という症状の調査記録。
第1手として Vercel Functions の実行リージョンだけを変更した。
`/chat` のクエリ最適化と `/cooking/[sessionId]` の `loading.tsx` 追加には
**まだ着手していない**（§7。効果を混ぜて測らないため）。

## 1. 分かったこと

### スケルトンには意図的な遅延が無い

`loading.tsx` は 6 つ（ホーム / 在庫 / AI / 履歴 / 設定 / 買い物リスト）。
`setTimeout`・最低表示時間・`animation-delay` のいずれも存在しない
（`animate-pulse` は Tailwind 既定）。

**スケルトンの表示時間 ≒ サーバーが描画を終えるまでの時間**である。
全ページが動的（`ƒ`）なので、prefetch が届けるのは `loading.tsx` までで、
本文は毎回サーバーへ往復する。タップ直後にスケルトンが即出て、
そのまま長く残るのはこのため。消せない何かが挟まっているわけではない。

### ローカル dev では、アプリの計算処理はほとんど時間を使っていない

以下はローカル dev（warm）の測定であり、**Production の内訳ではない**。
Production の内訳は測れていない（§5）。

Next 内蔵の per-request 内訳:

| ページ | next.js | proxy.ts | application-code |
| --- | --- | --- | --- |
| `/` | 9ms | 6–8ms | 182–312ms |
| `/inventory` | 9–19ms | 8–13ms | 100–160ms |
| `/chat` | 8–11ms | 7–9ms | **285–427ms** |
| `/history` | 8–12ms | 6–10ms | 106–185ms |
| `/settings` | 8–9ms | 7–8ms | 98–129ms |
| `/shopping` | 8–9ms | 6–8ms | 95–218ms |

`proxy.ts` は 6〜13ms で無罪。同じ環境から Supabase REST への素の往復は
96〜300ms で、単発クエリのページの `application-code` は**ほぼ往復時間そのもの**。

- N+1 は 1 件も無い
- `getAuthContext()` / `createClient()` は React `cache` でリクエスト内メモ化済み
- JWKS は `auth-js` のモジュール単位 `GLOBAL_JWKS` にキャッシュされるので、
  リクエスト毎に取りに行ってはいない（当初の疑いは除外）
- `revalidatePath` の範囲は過剰でない

残る既知の非効率は 2 つだけで、**どちらも今回は直していない**:

- `/chat` が `getOpenSession` → `getOrCreateConversation` → `loadMessages` の
  直列 3 往復（後段が前段の結果に依存するため単純な並列化はできない）
- `/cooking/[sessionId]` に `loading.tsx` が無く、遷移中に何も出ない

### 決定的な事実：DB を引かないページで既に 0.4 秒、時に 10 秒超

Production の `/login` は**データベースクエリを 1 本も撃たない**。
それでも 20 回計測の中央値は **0.474 秒**、速い群だけ見ても **0.403 秒**、
そして 4 回に 1 回は **7〜12 秒**かかっていた（§4）。

**少なくともこの時間は、DB クエリの最適化では短縮できない。**
このページは 1 本もクエリを撃っていないからである。

ただし**何が支配的かは特定できていない。** 候補は少なくとも 3 つある:

- 利用者 ↔ Functions のネットワーク往復
- Vercel Functions の起動（cold start を含む）
- アプリの初期化処理（Next のサーバー起動、モジュール評価、JWKS 初回取得など）

どれがどれだけ効いているかは未計測である。

## 2. 確認できた構造的問題：Functions と DB が別大陸にあった

| | 変更前 | Supabase |
| --- | --- | --- |
| 実行場所 | **iad1（米国東部 / us-east-1）** | **ap-northeast-2（ソウル）** |

`X-Vercel-Id` の 2 つ目のコードが `iad1` であることから、**関数は iad1 で
実行**されていた。`vercel.json` が無く、リージョン指定が無かったため Vercel の
既定に従っていた。

つまり 1 画面ぶんのデータを出すのに、

```
利用者（日本） → 日本側エッジ → iad1（米国東部） → ソウル（Supabase） → iad1 → 日本
```

という経路を通っていた。このうち **Functions ↔ Supabase の区間が、クエリの
本数に応じて繰り返される**（`/chat` は 3 往復）。利用者 ↔ Functions の区間は
1 画面につき原則 1 往復である。

### `X-Vercel-Id` の読み方（断定していないこと）

20 回ベースライン（§4）では 20 回とも **`kix1::iad1::…`** だった。
それ以前の計測では **`hnd1::iad1::…`** も観測している。

- **日本側エッジ（1 つ目のコード）は固定ではない。** `kix1` と `hnd1` の
  両方を観測しており、どちらに入るかは回によって変わる
- **確認できている固定部分は Functions の `iad1`（2 つ目のコード）だけ**である

## 3. 判断：Functions を DB と同居させる

`vercel.json` に `"regions": ["icn1"]`（ソウル）を指定した。**変更はこの 1 ファイルだけ。**

### なぜ hnd1（東京）ではなく icn1（ソウル）か

利用者が日本にいるので、直感的には東京（hnd1）が近い。それでも icn1 を選んだ:

- **往復の回数が違う。** 利用者 ↔ Functions は 1 画面につき原則 1 往復だが、
  Functions ↔ DB は**クエリの本数だけ**発生する（`/chat` は 3 回）。
  縮めて効くのは回数の多い方である
- 東京 ↔ ソウル（約 1,100〜1,200 km）は、元の日本 ↔ 米国東部（約 11,000 km）
  より**大幅に近い**
- `getClaims()` の JWT 検証はローカルで完結するので、認証のために
  利用者の近くにいる必要はない

利用者が増えて分布が変わったら、この判断は測り直す価値がある。

### TTFB の定義（比較のしかた）

数値は `curl` の `time_starttransfer` で、**DNS 解決・TCP 接続・TLS ハンドシェイク・
ネットワーク往復をすべて含む**。**サーバーの純粋な処理時間ではない。**

したがって絶対値そのものに意味を持たせない。
**同一端末・同一ネットワーク・同一コマンドで測った前後の差分**としてのみ扱う。

## 6. 計測の作法

**Preview と Production を分けて測る。** 混ぜて比較しない。

| | 注意 |
| --- | --- |
| **Preview** | Vercel の **Deployment Protection（SSO）** が手前に入る。認証リダイレクトの往復がそのまま数値に乗るので、**Production の変更前の値と直接比較してはいけない**。Preview で見るべきは「`X-Vercel-Id` の実行リージョンが `icn1` になったか」と「deployment が成功したか」だけ |

（`ttfb-baseline.sh`。同一端末・同一ネットワークから同じコマンドで実行すること）。

補助的に見るもの:

- `X-Vercel-Id` の 2 つ目のリージョンコードが `icn1` であること
- ローカル dev の `next.js` / `proxy.ts` / `application-code` の内訳
  （リージョン変更の影響を受けないので、アプリ側の回帰検出に使える）
- 認証済みページは **iPhone 実機**で体感を記録する。自動では取れない
